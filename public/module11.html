Technical · Lesson 1

How Webhooks Work — Complete Understanding

Webhooks are the foundation of every real-time automation. Once you understand them fully, you can connect any two platforms — even ones that do not have native Make.com integrations. This is the skill that separates basic automators from advanced ones who can build anything.

What a Webhook Is — Plain English
A webhook is a URL that receives data when something happens somewhere else. Think of it like a phone number you give to another app: "When something happens on your side, send the data to this URL." The app calls that URL with the data, and your automation runs instantly.
The opposite of a webhook is polling — where you check every 15 minutes to see if anything new happened. Polling is slow and wastes API calls. Webhooks are instant: data arrives in milliseconds of the triggering event. This is why WhatsApp bots and payment confirmations use webhooks — speed matters.
The 3 Parts of Every Webhook
1
The Sender
The app that sends data when something happens. Examples: 360dialog sends a webhook when a WhatsApp message arrives. Stripe sends a webhook when a payment succeeds. Typeform sends a webhook when someone submits a form. Calendly sends a webhook when someone books an appointment. Shopify sends a webhook when a new order comes in.
2
The URL (Endpoint)
The address that receives the data. In Make.com, when you add a "Custom Webhook" trigger module, Make.com generates a unique URL that looks like: https://hook.eu1.make.com/abc123xyz456.... You copy this URL and paste it into the sender app's webhook settings. This URL is now listening 24/7 for incoming data.
3
The Payload
The JSON data sent in the HTTP request body. This is the actual content — the message text, the payment amount, the form answers, the order details. Every webhook payload is structured differently depending on the platform sending it. Learning to read the payload is the core skill of webhook mastery.
What JSON Looks Like — Real WhatsApp Payload Example
When a WhatsApp message arrives via 360dialog, the payload sent to your webhook looks like this. Study this structure carefully — you will navigate it in Make.com using variable paths:
{ "object": "whatsapp_business_account", "entry": [ { "id": "123456789", "changes": [ { "value": { "messages": [ { "from": "447712345678", "id": "wamid.abc123", "timestamp": "1699876543", "text": { "body": "Hello, what are your opening hours?" }, "type": "text" } ], "contacts": [ { "profile": { "name": "John Smith" }, "wa_id": "447712345678" } ] }, "field": "messages" } ] } ] }
To access the message text in Make.com, the variable path is: entry[].changes[].value.messages[].text.body
To access the sender's phone number: entry[].changes[].value.messages[].from
To access the sender's name: entry[].changes[].value.contacts[].profile.name
How Make.com Handles Webhooks — Step by Step
1
Add the Custom Webhook trigger in Make.com
Open your Make.com scenario editor. Click the + to add the first module. In the search bar, type webhook. Under the Webhooks category, click Custom Webhook. A dialog appears asking you to create or select a webhook. Click Add. Give the webhook a descriptive name (e.g., "WhatsApp 360dialog"). Click Save. Make.com generates a unique URL — it appears in the webhook configuration dialog.
2
Copy the webhook URL
Click the Copy address to clipboard button next to the generated URL. It looks like: https://hook.eu1.make.com/abcdefg1234567. Keep this URL — you are about to paste it into the sending platform.
3
Register the URL with the sending platform
Go to the platform that will send data (360dialog, Stripe, Typeform, etc.). Find their Webhook settings — usually under Settings → Integrations → Webhooks. Paste your Make.com URL into the webhook URL field. Save. The platform will now send data to Make.com every time the triggering event happens.
360dialog: app.360dialog.io → Settings → Webhook URL field

Stripe: dashboard.stripe.com → Developers → Webhooks → Add endpoint

Typeform: your form → Connect → Webhooks → Add webhook
4
Capture the first webhook payload in Make.com
Back in Make.com, click Run once at the bottom of the scenario editor. Make.com is now listening for one incoming request. Go to the sending platform and trigger the event manually — send a test WhatsApp message to the bot number, or complete a test form submission. Return to Make.com. The Custom Webhook module now shows a small bubble indicating it received data. Click OK.
After capturing the first payload, Make.com learns the data structure. When you click on any subsequent module and open its field configuration, you can use the variable picker (click the small icon inside any field) to browse and insert variables from the captured payload. The variable paths are automatically resolved for you.
Common Webhook Senders and Their Payload Formats
A
Stripe — payment.succeeded event
Key fields: data.object.amount (payment amount in cents), data.object.customer_email (customer email), data.object.metadata (any custom fields you added).
B
Typeform — form submission
Key fields: form_response.answers[].text (text answers), form_response.answers[].email (email answers), form_response.hidden (hidden fields for tracking).
C
Calendly — invitee.created event
Key fields: payload.invitee.name (name), payload.invitee.email (email), payload.event.start_time (appointment start), payload.questions_and_answers (custom questions).
D
Shopify — orders/create event
Key fields: customer.email, customer.first_name, line_items[].title (product names), total_price, shipping_address.address1.
How to Inspect Any Webhook Before Building
1
Go to webhook.site in your browser
Open a new browser tab and navigate to webhook.site. The page loads and immediately gives you a unique URL — something like https://webhook.site/abc-123-xyz-456. You do not need to register or log in. This URL is free and stays active for a few hours.
2
Paste this URL into the sending platform temporarily
Go to 360dialog (or Stripe, Typeform, or any platform). Temporarily replace your Make.com webhook URL with the webhook.site URL. Save the setting. Trigger the event — send a WhatsApp message to the bot number, or complete a form, or make a test payment.
3
Read the full JSON payload on webhook.site
Return to the webhook.site tab. You see a new entry in the left column — click on it. The right panel shows the complete HTTP request: headers, query parameters, and the full JSON body. Read the structure carefully. Note the exact field names and the nesting depth. This tells you exactly which variable paths to use in Make.com.
This technique saves 1–2 hours per new platform integration. Always use webhook.site first when connecting a platform you have not worked with before. Once you understand the payload structure, switch back to your Make.com URL in the platform settings and build with confidence.
The Single Most Important Habit in Webhook Work
Before connecting any new platform to Make.com, always inspect the webhook payload on webhook.site first. This takes 5 minutes and prevents 2 hours of debugging wrong variable paths. Professionals do this every time — even when they think they know the payload format. APIs change their structures without warning. Always verify before you build.
Exercise — Inspect a Live Webhook Payload
Go to webhook.site right now. Copy the URL it gives you. Open your 360dialog dashboard. Go to Settings and temporarily paste the webhook.site URL as your WhatsApp webhook. Save it. Now open WhatsApp and send a test message to your bot number. Return to webhook.site and click the new entry on the left. Read the entire JSON payload. Find the message body and the sender's phone number in the structure. Write down their exact variable paths. Then restore your Make.com URL in 360dialog. You now understand exactly what Make.com receives for every WhatsApp message.
Key Takeaways — Lesson 1
Webhooks are instant — data arrives in milliseconds, not every 15 minutes like polling.
Every webhook has 3 parts: the sender, the URL endpoint, and the JSON payload.
Use webhook.site to inspect any platform's payload before building in Make.com.
After capturing the first payload in Make.com, the variable picker shows all available fields automatically.
Advanced · Lesson 2

Advanced Webhook Patterns in Make.com

These 5 patterns solve real production problems — routing different event types, handling errors, responding back to the sender, managing concurrent webhooks, and collecting batches of data. Every professional automation agency uses at least 3 of these regularly.

Pattern 1 — The Router: Send Data Down Different Paths
Use case: a WhatsApp bot receives messages about different topics. Messages about "price" should go to a pricing flow. Messages about "booking" should go to a booking flow. Messages about "complaint" should escalate to a human. One webhook, three paths — the Router handles this.
1
Add the Router module after your Webhook trigger
In the Make.com scenario editor, after your Webhook trigger module, click the + button. In the module search bar, type router. Under the Flow Control category, click Router. The Router appears and automatically creates two empty paths branching from it. You can add more paths by clicking Add route on the Router module.
2
Set filter conditions on each path
Click the wrench icon on the line connecting the Router to the first module on Path 1. A Filter configuration dialog opens. In the "Condition" section, click the field on the left and select the message body variable: entry[].changes[].value.messages[].text.body. Set the operator to Contains (case insensitive). In the value field on the right, type price. Click OK.
Path 1 now only activates when the message contains the word "price." Repeat for Path 2 with "booking" and Path 3 with "complaint." You can use multiple conditions on one path using AND/OR logic — click the + button in the filter dialog to add more conditions.
3
Build different modules on each path
Path 1 (price): add an OpenAI module with a pricing-specific prompt, then an HTTP module that sends the WhatsApp reply. Path 2 (booking): add a Google Calendar module to check availability, then a reply module. Path 3 (complaint): skip OpenAI and add a direct HTTP module that sends an alert to the business owner via Slack or email, then a polite WhatsApp reply to the customer. Each path is fully independent.
Pattern 2 — The Aggregator: Process Data in Batches
Use case: collect all new leads from a form over the past hour and send one consolidated email summary to the sales team instead of 40 individual emails.
4
Add an Array Aggregator after the data-generating modules
In the scenario editor, after the module that produces multiple data bundles, click +. Search for array aggregator. Select it from the Flow Control category. In its configuration, set "Source Module" to the module that generates the individual items. Set the fields you want to aggregate. The aggregator collects all bundles into a single array before passing them to the next module.
5
Use the aggregated data in a single email or message
After the Array Aggregator, add an Email module or a Slack module. In the message body, use the aggregated output variable — it contains all items formatted as a list. This sends one notification with all the data instead of one notification per item. Clients love this pattern for daily or hourly summary digests.
Pattern 3 — Error Handling: What to Do When a Module Fails
6
Add a Break directive on modules that might fail
Right-click on the module you want to add error handling to (for example, the OpenAI module). A context menu appears. Click Add error handler. A "Break" path appears in red below the module. Any module you add to this red path will run when the main module fails — instead of the scenario stopping entirely.
7
Set up email alerts when an automation fails
On the error handler path (the red path), add an Email module. Configure it to send to your email address. In the Subject field, type: Automation error — [scenario name]. In the Body field, include: the error message variable, the scenario name, and the time. Click OK. Now when anything fails in that scenario, you receive an email immediately — you know before the client does.
This is a professional practice that prevents silent failures. Without error handlers, Make.com stops the scenario and logs the error — but you only see it if you manually check the scenario history. Email alerts mean problems are caught and fixed before clients notice the automation stopped working.
Pattern 4 — Webhook Response: Send Data Back to the Sender
Use case: a chatbot platform sends a webhook to Make.com and expects the AI response in the HTTP response body — not as a separate API call. The platform waits for your response before displaying the reply to the user.
8
Add the Webhook Response module at the end of your scenario
Click + after your final processing module. Search for webhook response. Under the Webhooks category, select Webhook Response. The configuration dialog opens. Set Status to 200. In the Body field, use the variable picker to select your OpenAI output: {{2.choices[].message.content}}. In the Headers section, add a header: Content-Type = application/json. Click OK.
Make.com must reach the Webhook Response module within 40 seconds of receiving the incoming webhook — otherwise the sending platform times out. For slow operations, consider running heavy processing asynchronously and sending a quick acknowledgment first.
Pattern 5 — Webhook Queuing and Concurrent Executions
9
What happens when 100 messages arrive simultaneously
Make.com runs multiple scenario executions in parallel by default. If 100 WhatsApp messages arrive within 1 second, Make.com starts 100 parallel executions of your scenario. For most scenarios this is fine — but if your scenario modifies shared state (like a database record or a Google Sheet), parallel execution can cause race conditions.
10
Enable Sequential Processing to prevent race conditions
To make your scenario process one webhook at a time: open your scenario settings (click the three dots or the gear icon on the scenario). Find the Sequential processing option. Toggle it to On. Save. Now Make.com queues incoming webhooks and processes them one at a time. This prevents data conflicts but means high-volume scenarios may fall behind — monitor the execution queue in the scenario history.
11
Understanding the execution queue
When sequential processing is on, incoming webhooks are added to a queue. Make.com processes them in order. In the scenario history (click the clock icon at the bottom), you see queued executions waiting to run. If the queue grows very long (50+), your scenario may not be able to keep up with the volume. In that case, consider splitting the scenario into lighter modules or upgrading your Make.com plan for more concurrent executions.
Which Pattern to Use When
Router: when different event types need different actions. Aggregator: when you need summaries instead of individual notifications. Error Handler: on every production scenario — always. Webhook Response: when the sending platform expects a reply in the HTTP response. Sequential Processing: when your scenario writes to shared resources and you cannot afford race conditions. You will use the Router and Error Handler on almost every scenario you build.
Key Takeaways — Lesson 2
Use the Router with Filter conditions to send different webhook events down different paths in one scenario.
Add error handlers with email alerts on every production scenario — silent failures are the biggest client risk.
The Webhook Response module sends data back to the platform that triggered the webhook — use it for synchronous chatbot platforms.
Enable Sequential Processing when your scenario writes to shared state to prevent race conditions.
Debugging · Lesson 3

Debug and Troubleshoot Any Webhook Problem

Webhook problems are the most common technical issue in automation work. This lesson gives you a step-by-step debugging framework that solves 95% of webhook problems in under 10 minutes — no guessing, no trial and error.

Problem 1 — "My Webhook Trigger Shows No Data"
1
Check that the webhook URL is correctly pasted in the sending app
Go to Make.com. Open your scenario. Click on the Webhook trigger module. In the module panel, find the webhook URL — copy it. Now go to the sending platform (360dialog, Stripe, Typeform, etc.) and open their Webhook settings. Compare the URL there to what you just copied. Even one wrong character — a missing letter, an extra space, or a truncated URL — breaks the connection. Paste the correct URL fresh from Make.com.
A common mistake: copying the URL from an old email or a notes app where it got truncated. Always copy directly from Make.com's webhook module panel.
2
Verify the sending app is actually sending to this URL
Some platforms have a test/staging mode and a production mode. Confirm you are pasting the webhook URL into the production webhook settings — not a test environment. Also confirm the scenario is actively listening: in Make.com, the scenario must have Scheduling turned ON or be in "Run once" mode to receive webhooks. Click the power toggle at the bottom of the scenario editor to turn scheduling on.
3
Use "Run once" mode to capture a test event
In Make.com, click Run once at the bottom-left of the scenario editor. Make.com is now waiting for one incoming request. Go to the sending platform and trigger the event manually — send a test WhatsApp message, submit a test form, or click "Send test webhook" in the platform's webhook settings. Return to Make.com — watch whether the Webhook module lights up and shows a number indicating data was received.
If Make.com receives the data in Run Once mode but NOT during normal scheduling — your scenario scheduling is probably off. Turn it on. If Make.com receives nothing even in Run Once mode — the problem is definitively in the sender or the URL.
4
Use webhook.site to isolate the problem
Go to webhook.site. Copy the URL it provides. Go to the sending platform. Temporarily replace your Make.com URL with the webhook.site URL. Trigger the event again. Check webhook.site — does data arrive? If yes: the platform is sending correctly, the problem is in Make.com (wrong URL, scheduling off). If no: the platform is not sending at all — check the platform's own settings, event subscriptions, or account permissions.
Problem 2 — "Module Shows Red — 400 Bad Request"
5
Understand what 400 means
A 400 Bad Request error means the API you are calling rejected your request because the data you sent was malformed or incomplete. This is NOT a server error — it means your request had a problem. The fix is always in how you are building the request body or URL.
6
Check the error details in the execution history
In Make.com, click the clock icon at the bottom of the scenario editor. Click the failed execution (shown with a red icon). Click on the specific module that failed (shown with a red border). In the right panel, look for the "Error" section — it shows the exact response the API returned. Read it carefully. The API usually tells you exactly what is wrong: "Required field 'to' is missing" or "Invalid phone number format."
7
Validate your JSON with jsonlint.com
If your module sends a JSON body, go to jsonlint.com. Copy the JSON you are sending (from the module's Body field in Make.com). Paste it into jsonlint.com and click Validate JSON. Common errors: a trailing comma after the last field in an object, a missing quote around a string value, or mismatched brackets. jsonlint.com highlights the exact line with the error.
Problem 3 — "Module Shows Red — 401 Unauthorized"
8
Your API key is wrong, expired, or formatted incorrectly
A 401 error means authentication failed. The API rejected your API key. Causes: the key was copied incorrectly (extra space, truncated), the key was regenerated on the API provider's side and the old one is no longer valid, or the Authorization header format is wrong.
9
Re-enter the API key through Make.com Connections
In Make.com, click your name/avatar in the top-right corner and select Connections. The Connections page shows all your API connections. Find the connection that is failing. Click Edit (the pencil icon). Delete the existing API key value. Go back to the API provider's dashboard, copy a fresh API key, and paste it into the Make.com connection field. Click Save. Return to your scenario and re-run.
For HTTP modules that use headers directly (not Make.com Connections): click on the failing module, find the Headers section, look for the Authorization header, and re-paste the API key there. Common format errors: writing Bearer[KEY] instead of Bearer [KEY] (note the space after "Bearer"), or using the wrong header name (e.g., some APIs use X-API-Key not Authorization).
Problem 4 — "Automation Runs but Sends Wrong Data"
10
Read the Output of each module in the execution history
Click the clock icon to open Scenario History. Click the execution where wrong data was sent. A visual map of the scenario appears. Click on each module in sequence. For each module, you see two panels: Input (what it received) and Output (what it sent to the next module). Trace the data flow step by step until you find where the correct data was transformed into incorrect data.
11
Verify the exact variable value being used
Found the problem module? Click on it in the scenario editor (not in history — in the live editor). Open the field that is sending wrong data. You see a variable reference like {{1.entry[].changes[].value.messages[].text.body}}. To verify this variable's current value: go back to execution history, click the same execution, click the Webhook trigger module, and look at its Output. Find the field that corresponds to your variable path. If it is empty or wrong, your variable path is incorrect — update it.
The Make.com Execution History — Your Primary Debugging Tool
12
How to open and read the Execution History
In the Make.com scenario editor, look at the very bottom of the screen. You see a row of icons. Click the clock icon (hover shows "History"). The History panel opens on the right side. Each row is one execution — the most recent one is at the top. Each row shows: a green checkmark (success) or red X (failure), the timestamp, and the number of operations used.
Click any row to expand it. You see a visual representation of your scenario with the data flow highlighted. Every module that ran is shown. Click on a module circle to see its Input bundle (what data it received) and its Output bundle (what data it produced and passed to the next module). This is the most accurate view of what actually happened inside a scenario execution.
13
Use Execution History as your first debugging step — always
Before checking anything else when a scenario breaks, open Execution History. Look at the failed execution. Find the first red module. That is where the failure started. Everything else is a consequence of that first failure. Fix the root cause, not the symptoms. After fixing, click Run once and trigger a test event to confirm the fix.
The Golden Rule of Webhook Debugging
Work from the beginning, not from the end. When something breaks, the instinct is to look at the last module that failed. But the real problem is almost always earlier in the chain — wrong variable path, wrong API key, wrong data format at the source. Start with Execution History, find the first red module, read its error. That is your answer. Fix one thing at a time and test after each fix — do not change three things simultaneously or you won't know which one solved it.
Exercise — Practice Debugging With a Real Error
Intentionally break one of your existing Make.com scenarios: open any HTTP module and change the API key to a random wrong value. Run the scenario. Now debug it: open Execution History, find the failed module, read the error. Can you identify it as a 401 Unauthorized? Now fix it: go to Connections, update the key to the correct value. Run again. Watch the scenario succeed. This exercise builds the muscle memory of the debugging flow so that when a real production error occurs, you respond methodically instead of frantically.
Key Takeaways — Lesson 3
Always check Make.com Execution History first — it shows exactly which module failed and why.
Use webhook.site to isolate whether the problem is in the sender or in Make.com — it tells you definitively within 2 minutes.
400 errors = your request is malformed. 401 errors = your API key is wrong or expired. Always check the error details in the module output.
After fixing any variable path issue, use "Run once" to capture fresh data and re-select the corrected variables.
