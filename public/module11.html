Technical · Lesson 1

How Webhooks Work — Complete Understanding

Webhooks are the foundation of every real-time automation. Understanding them deeply means you can connect any two platforms — even ones that don't have native Make.com integrations. This is what separates basic automators from advanced ones.

What is a Webhook — Plain English Explanation
A webhook is a URL address that listens for incoming data. When something happens on Platform A (a message arrives, a form is submitted, a payment is made), Platform A sends the data to Platform B's webhook URL. Platform B receives it instantly and can process it.
Think of it like a phone number. You give your webhook URL to another platform. When something happens, they "call" that URL and send the data. Your automation answers the call and does something with the data.
This is different from polling (which checks for new data every X minutes). Webhooks are instant — data arrives in milliseconds of the event happening.
The Exact Technical Flow
1
You create a webhook URL in Make.com
In Make.com, when you add a "Custom Webhook" trigger, Make.com generates a unique URL like https://hook.eu1.make.com/abc123xyz.... This URL is now listening 24/7 for incoming HTTP POST requests.
2
You register the webhook URL with another platform
You go to 360dialog (WhatsApp), Meta Developer Console (Instagram), Stripe, Shopify, or any other platform and tell it: "When X happens, send the data to this URL." This is called "registering" or "subscribing" to a webhook.
3
An event happens on that platform
A WhatsApp message arrives. A Stripe payment succeeds. An Instagram DM comes in. Immediately — in milliseconds — that platform makes an HTTP POST request to your webhook URL, sending all the event data as JSON in the request body.
4
Make.com receives the data and runs your scenario
Make.com's webhook URL receives the POST request. Your scenario activates instantly. The JSON data from the request body becomes available as variables you can use in all subsequent modules.
Important: Make.com responds to the incoming webhook with HTTP 200 OK within a few seconds. Most platforms require this 200 response to confirm delivery. If Make.com is too slow or offline, the platform will retry the webhook delivery — usually 3–5 times over the next few hours.
Reading and Parsing JSON Webhook Data in Make.com
Every webhook sends data as JSON. Understanding how to read and navigate JSON in Make.com is essential. Here is a real example of what a WhatsApp webhook payload looks like:
{ "object": "whatsapp_business_account", "entry": [ { "id": "123456789", "changes": [ { "value": { "messages": [ { "from": "40712345678", "id": "wamid.abc123", "timestamp": "1699876543", "text": { "body": "Hello, what are your hours?" }, "type": "text" } ] } } ] } ] }
To access the message text in Make.com variables, you navigate: entry[].changes[].value.messages[].text.body
To access the sender's phone number: entry[].changes[].value.messages[].from
How to Use Webhooks.site to Inspect Any Webhook
1
Go to webhook.site
Open webhook.site in your browser. The page immediately gives you a unique URL like https://webhook.site/abc-123-xyz. This URL is free and lives for a few hours.
2
Use this URL as your webhook in any platform
When you need to understand what data a platform sends, paste this webhook.site URL into the platform's webhook settings instead of your Make.com URL. Then trigger the event on that platform.
3
See the exact JSON payload
Webhook.site shows you the complete HTTP request in real time — headers, body, query parameters — everything. You can see exactly what data structure the platform sends. Use this to understand the correct variable paths before building in Make.com.
This technique saves hours of debugging. Before connecting any new platform to Make.com, always use webhook.site first to understand the exact data structure. Then build your Make.com scenario with the correct variable paths.
Key Takeaways — Lesson 1
Webhooks are instant — data arrives in milliseconds, not every 15 minutes like scheduled triggers.
Every webhook sends JSON data. The variable path tells you how to navigate the nested structure.
Always use webhook.site first to inspect the data structure before building in Make.com.
Make.com must respond with HTTP 200 OK or the sending platform will retry the webhook delivery.
Advanced · Lesson 2

Advanced Webhook Patterns in Make.com

Once you understand basic webhooks, these advanced patterns let you handle complex real-world scenarios — multiple event types, webhook verification, error handling, and routing different events to different actions.

Pattern 1 — Router for Multiple Event Types
Many platforms send different types of events to the same webhook URL. For example, Instagram sends both DMs and post comments to the same webhook. You need to route them to different paths in your scenario.
1
Add a Router module after your Webhook trigger
In Make.com, click + after the Webhook module. Search for Router — it is in the Flow Control category. The Router splits your scenario into multiple parallel paths.
2
Set up Filter conditions on each path
Click the wrench icon on the connection line between the Router and the first module in each path. A Filter dialog appears. Set a condition that identifies this event type.
Example for Instagram:
Path 1 (DMs): Field = entry[].messaging — Condition = Exists
Path 2 (Comments): Field = entry[].changes[].value.comments — Condition = Exists

This routes DM events to Path 1 and comment events to Path 2.
3
Build different actions on each path
Path 1 continues with OpenAI → HTTP Send DM reply. Path 2 continues with a different OpenAI prompt → HTTP Send comment reply. Each path handles its event type independently.
Pattern 2 — Webhook Verification (GET + POST)
Some platforms (Meta/Facebook/Instagram) send a GET request to verify your webhook before they start sending real events. Make.com's Custom Webhook only handles POST requests by default. Here is how to handle the GET verification:
1
The verification flow
When you register a webhook with Meta, they send a GET request to your URL with three query parameters: hub.mode, hub.challenge, and hub.verify_token. Your server must respond with the hub.challenge value.
2
Handle verification in your Render server
Add this route to your server.js on Render — this handles the Meta verification automatically:
// Meta webhook verification app.get('/webhook', (req, res) => { const mode = req.query['hub.mode']; const token = req.query['hub.verify_token']; const challenge = req.query['hub.challenge']; const VERIFY_TOKEN = process.env.WEBHOOK_VERIFY_TOKEN || 'myverifytoken'; if (mode === 'subscribe' && token === VERIFY_TOKEN) { console.log('Webhook verified'); res.status(200).send(challenge); } else { res.sendStatus(403); } }); // Receive actual webhook events app.post('/webhook', (req, res) => { const body = req.body; // Forward to Make.com fetch(process.env.MAKE_WEBHOOK_URL, { method: 'POST', headers: { 'Content-Type': 'application/json' }, body: JSON.stringify(body) }); res.sendStatus(200); });
Set WEBHOOK_VERIFY_TOKEN in Render environment variables to match the verify token you enter in Meta's webhook settings. Set MAKE_WEBHOOK_URL to your Make.com webhook URL.
Pattern 3 — Webhook Response with Data
Some integrations require your webhook to respond with specific data — not just HTTP 200. For example, Stripe requires you to respond with a success confirmation, and some chatbot platforms expect your webhook to return the response text directly.
1
Use the Webhook Response module in Make.com
After your processing modules, add a Webhooks → Webhook Response module. This sends a custom HTTP response back to the platform that sent the webhook. Set the Status to 200, set the Body to whatever data the platform expects.
2
Return the AI response directly
For chatbot platforms that expect the reply in the webhook response, set the Body to the OpenAI output variable: {{2.choices[].message.content}}. Set Content-Type header to application/json.
Key Takeaways — Lesson 2
Use Router + Filters to handle multiple event types from one webhook URL.
Meta platforms require GET verification before sending POST events — handle this in your Render server.
The Webhook Response module lets you send custom data back to the platform that triggered the webhook.
For complex webhook setups, use your Render server as a middleware between the platform and Make.com.
Debugging · Lesson 3

Debug and Troubleshoot Any Webhook Problem

Webhook problems are the most common technical issue you will face. This lesson gives you a systematic debugging process that solves 95% of webhook problems in under 10 minutes.

The 5-Step Debugging Process
1
Verify the webhook URL is correct and active
Go to Make.com → open your Scenario → click on the Webhook module → check that the webhook URL shown is exactly what you registered with the platform. Even one character difference breaks everything. Turn on Scheduling in Make.com so the webhook is actively listening.
2
Check Make.com Scenario History
In Make.com, at the bottom of the Scenario editor, click the clock icon — this shows the History of all runs. Each run shows: when it happened, whether it succeeded or failed, and exactly where it failed. Click on a failed run to see the error message on the specific module that failed.
If the History is empty — Make.com is not receiving the webhook at all. The problem is in the registration or the URL. If History shows runs but with errors — the webhook arrives but something in your scenario is wrong.
3
Use webhook.site to verify the platform is sending data
Temporarily replace your Make.com webhook URL with a webhook.site URL in the platform settings. Trigger the event. If webhook.site receives data — the platform is sending correctly and the problem is in your Make.com setup. If webhook.site receives nothing — the problem is in how you registered the webhook.
4
Check variable paths carefully
The most common error after the webhook arrives is wrong variable paths. Click on the Webhook module circle in your scenario and look at the data structure. Compare it carefully with the variable paths you are using in subsequent modules. Even a small difference like messages[].text.body vs messages[0].text.body can cause failures.
5
Check the platform's webhook logs
Most platforms (Stripe, Shopify, Meta) have a webhook log section in their dashboard. Go there and look at recent webhook deliveries. You can see: whether the delivery was attempted, what HTTP status code your webhook returned, and whether there were any errors. This is the most accurate source of truth for webhook problems.
Stripe webhook logs: dashboard.stripe.com → Developers → Webhooks → click your endpoint → Events tab

Meta webhook logs: developers.facebook.com → your app → Webhooks → look at the subscription status

360dialog: app.360dialog.io → your channel → Settings → check the webhook status indicator
Most Common Webhook Errors and Their Fixes
⚠
Error: Webhook not receiving data at all
Causes and fixes:
1. Make.com Scheduling is OFF → turn it ON
2. Wrong webhook URL registered → copy the exact URL from Make.com and re-paste it
3. Platform requires HTTPS but your URL is HTTP → Make.com webhooks are always HTTPS, this should not happen
4. Platform requires webhook verification (GET) → add verification handler to your Render server
⚠
Error: Data arrives but wrong variable
The webhook data structure does not match your variable paths. Fix:
1. Click "Run once" in Make.com
2. Trigger the event on the platform
3. Make.com captures the data
4. Click OK on the Webhook module
5. Now click on each subsequent module and use the variable picker to re-select the correct variables from the fresh data structure
⚠
Error: "Bundle is undefined" or "Cannot read property"
This means Make.com expected data at a certain path but found nothing. Usually happens when the webhook payload structure changes or when the event type is different from expected.
Add a Filter before the problem module that checks if the expected field exists. Set condition: field Exists. This prevents the scenario from failing when unexpected data arrives.
⚠
Error: HTTP 403 or 401 on webhook response
The platform is rejecting your webhook responses. Usually means your API key or authentication is wrong.
Check the Headers section of your HTTP module. Make sure the API key is correct, the header name is exactly right (case-sensitive), and the format is correct. For example, some APIs use Authorization: Bearer YOUR_KEY while others use a custom header like D360-API-KEY: YOUR_KEY.
✓ The Golden Rule of Webhook Debugging
When something breaks, always start from the beginning: is the webhook URL correct? Is Make.com listening? Is the platform sending? Work through the flow step by step. Do not skip steps. 90% of webhook problems are simple configuration errors that take 2 minutes to fix once you identify them.
Key Takeaways — Lesson 3
Always check Make.com Scenario History first — it tells you exactly where the failure happened.
Use webhook.site to isolate whether the problem is in the platform sending or in Make.com receiving.
After fixing a variable path issue, use "Run once" to capture fresh data and re-select variables.
Most webhook problems are configuration errors — wrong URL, wrong API key, or wrong variable path.
